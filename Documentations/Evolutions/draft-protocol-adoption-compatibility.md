# Draft - 协议新采纳另一个协议时按破坏性改动判定

- **状态**: Accepted
- **创建日期**: 2026-10-27
- **最后更新**: 2026-10-27
- **实现分支**: `fix/code-review-findings`（与提出它的那次代码审查的修复同一条分支）

## 摘要

ObjC API diff 现在只把「协议新增一个必选成员」判为破坏性改动，理由是现有的实现方没有这个成员的实现，
调用方按新契约发消息会遇到 `unrecognized selector`（见 `ObjCMemberRecord.compatibilityOverride`）。
协议新采纳另一个协议（`@protocol P <Q>`）会把 Q 的全部必选成员同样加到 P 的实现方头上，却被判为兼容：
diff 报 P 被修改、`+ adopts <Q>`、标 additive，`--fail-on-breaking` 放行。这份提案让两种情况按同一条理由判定。

## 方案

- **只改协议容器。** 类和分类新采纳协议仍是兼容改动：它们是在提供实现，不是在向别人提要求。
- **协议容器新增 `adopts:<Q>` 记录时**，在新快照里把 Q 连同它自己采纳的协议逐层展开：只要展开后有任何
  必选成员不在 P 原有的必选成员里，就判为破坏性；没有新增的必选成员（Q 的成员全部可选，或 P 本来就经别的
  协议要求了它们）仍判为兼容。
- **Q 不在新快照里**（采纳了一个本镜像没有记录的协议，无法展开）时判为破坏性，宁可误报，不漏报。
- **移除采纳**仍按现状判为破坏性，不变。
- 规则放在 `compatibilityOverride` 同处，双边 differ 与 evolution builder 共用同一条，保证两条路径结论一致；
  需要按名字查协议，所以判定时要能拿到新快照里的协议表。
- 落地时在 `Internal/ObjCAPIDiffDesignAndLimitations.md` 的语义差异一节补上这一条。
